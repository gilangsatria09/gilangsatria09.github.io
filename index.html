Case study

Why IBID v3.0 is modular

v2.0 was built by a team, and the structure showed it. For v3.0 I rewrote the app alone and organized it so that several developers can build features at the same time without getting in each other's way.

The problem in v2.0
The project structure was a poor decision, and so was the navigation library, which was also implemented poorly. Early in development every developer worked in their own style, so the codebase became messy.
The decision
Split the app into feature modules, backed by Clean Architecture and BLoC. I chose modularization for scalability and maintainability, and to reduce conflicts when several features are built in parallel.
The rules
Each feature module must stand by itself. Anything shared lives in a shared feature module or the core module, and features pull those in through a path dependency in pubspec.yaml, managed with Melos.
Consistency
The same conventions apply in every module: how routes work, and how the data model, entity, use case, repository and data source are written. I wrote them into AI-assisted development guidelines (Claude Code skills and markdown rule files), so generated code follows them too.

CC Expense Tracker

Personal project · Flutter · 2026

An app I built to track my own credit-card and pay-later spending. It handles statement cut-off dates, split group orders, installments and recurring subscriptions. All data stays on the device, with no backend or account.

  • Clean Architecture with BLoC, get_it for dependency injection and Drift (SQLite) for local storage.
  • An optional receipt reader that sends a photo to the Gemini API and fills in the split-bill items.
  • Local reminders, JSON import, and backup and restore.
  • Unit and widget tests written with bloc_test and mocktail.
  • Layered but not modular, on purpose. One developer and one small app have no need for module boundaries, which is the opposite of the IBID v3.0 case above.
